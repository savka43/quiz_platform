
Из `backend/`:

```bash
uv sync
# Для нового окружения: скопировать .env.example в .env и указать реквизиты БД.
docker compose up -d db
uv run alembic upgrade head
uv run fastapi dev main.py
```

JWT использует RSA-ключи в `backend/api_v1/auth/certs/`. Существующую пару ключей сохранять: её замена сделает выданные токены недействительными. Только для нового окружения без ключей:

```bash
mkdir -p api_v1/auth/certs
openssl genpkey -algorithm RSA -out api_v1/auth/certs/jwt-private.pem -pkeyopt rsa_keygen_bits:2048
chmod 600 api_v1/auth/certs/jwt-private.pem
openssl rsa -pubout -in api_v1/auth/certs/jwt-private.pem -out api_v1/auth/certs/jwt-public.pem
```

Каталог ключей исключён из Git. Пути и сроки жизни настраиваются через `.env.example`. На всех экземплярах API должна использоваться одна и та же пара ключей. Пароли, JWT и SQL-параметры не логируются приложением; подробное SQL-логирование отключено.

## Маршруты

| Метод | Путь | Вход / назначение |
| --- | --- | --- |
| POST | `/api/v1/auth/register` | JSON `email`, `password`; создаёт пользователя |
| POST | `/api/v1/auth/login` | Form `username` = email, `password`; возвращает пару токенов |
| GET | `/api/v1/users/me` | `Authorization: Bearer <access_token>`; пользователь из БД |
| GET | `/api/v1/users/{id}` | Только свой профиль, с access-токеном |
| POST | `/api/v1/auth/refresh` | `Authorization: Bearer <refresh_token>`; новая пара токенов |
| POST | `/api/v1/auth/logout` | `Authorization: Bearer <refresh_token>`; отзыв refresh, ответ 204 |

Регистрация принимает только `email` и `password`, длина пароля от 8 символов и не более 72 байт UTF-8 (ограничение bcrypt; для кириллицы символов помещается меньше). Email нормализуется в нижний регистр. Поля `active`, `user_id`, `hashed_password` присылать нельзя. Сервер устанавливает `active=True`, хеширует пароль bcrypt и возвращает `UserRead` без хеша. Повторный email даёт 409, ошибки валидации — 422.

Пример регистрации:

```json
{
  "email": "user@example.com",
  "password": "A-long-personal-password"
}
```

Ответ входа и обновления:

```json
{
  "access_token": "...",
  "refresh_token": "...",
  "token_type": "bearer"
}
```

Неверный пароль, недействительный/просроченный токен, неподходящий тип токена или отсутствующий пользователь дают 401. Неактивный пользователь не может войти, читать профиль или обновлять токены — 403.

Существующие корректные bcrypt-хеши проверяются без замены. Произвольные строки, сохранённые старым CRUD вместо настоящего хеша, не являются рабочими паролями: вход с ними возвращает 401. Их нельзя автоматически превратить в пароль пользователя.

## Проверка через Swagger

1. Открыть `/docs`, выполнить `POST /auth/register`.
2. В `Authorize` выбрать `OAuth2PasswordBearer`: в `username` указать email, в `password` — пароль. Swagger вызовет `/auth/login` и сохранит access-токен.
3. Выполнить `GET /users/me`.
4. Чтобы получить refresh-токен для ручной проверки, отдельно выполнить `/auth/login` с теми же данными. Скопировать `refresh_token` из ответа.
5. В `Authorize` в поле `RefreshToken` вставить только значение refresh-токена, без слова `Bearer`.
6. Выполнить `/auth/refresh`. Сохранить **оба новых токена**, заменить значение `RefreshToken` перед следующим обновлением или выходом. Старый refresh повторно даст 401.
7. Выполнить `/auth/logout` с последним refresh-токеном. Последующее обновление с ним даст 401.

Ручной `/auth/refresh` в Swagger автоматически не заменяет access-токен схемы OAuth2; на frontend сохранение новой пары должен выполнять клиент.

## Сроки и хранение сессий

JWT содержит `sub` (ID пользователя), `type`, `iat`, `exp`, `jti`. Проверяются подпись, срок действия, обязательные поля и тип. Access по умолчанию живёт 15 минут, refresh — 30 дней. При ротации новый refresh получает новый 30-дневный срок.

В `refresh_sessions` сохраняются ID пользователя, уникальный `jti`, срок действия и время отзыва. Сам JWT в БД не сохраняется. Данные переживают перезапуск API. Удаление пользователя каскадно удаляет его refresh-сессии.

Ротация выполняется одной транзакцией: старый refresh отзывается и создаётся новый. Условный UPDATE допускает только один успешный запрос при параллельном обновлении. Ошибка до commit откатывает и отзыв старого токена. Клиент должен выполнять refresh последовательно и сохранять новую пару: если ответ успешной ротации потерян, повторный запрос со старым refresh не пройдёт, потребуется вход.

Выход отзывает только переданный refresh. Уже выданный access действует до истечения его короткого срока; клиент при выходе удаляет оба токена. Выход на одном устройстве не завершает другие сессии. Массовый отзыв, восстановление/смена пароля, подтверждение email и ограничения частоты входа не входят в эту реализацию. Отозванные и истёкшие строки пока сохраняются; периодическую очистку можно добавить отдельно.

Старые публичные операции создания/изменения/удаления пользователей и выдача списка пользователей отключены: они позволяли задавать хеш пароля извне. Их схемы и CRUD-функции оставлены в коде для дальнейшей разработки. Demo Auth не подключён к приложению.

**Права ресурсов:** CRUD тестов и вопросов проверяет владельца теста, CRUD попыток и ответов — участника. Все списки ограничены текущим пользователем. Публичные тесты пока не поддерживаются. При создании теста и попытки `user_id` берётся из JWT, передавать его в теле запроса нельзя. Перенос записей между родительскими объектами через PATCH запрещён.

## Проверки

Из `backend/`, с работающей PostgreSQL и применёнными миграциями:

```bash
uv run python -m pytest -q
uv run alembic check
```

По умолчанию тесты используют БД из настроек; для отдельной тестовой БД установить `TEST_DATABASE_URL` в формате `postgresql+asyncpg://...`, предварительно применив к ней миграции. Основные тесты работают внутри откатываемых транзакций. Тест параллельной ротации создаёт уникального пользователя в реальной БД и удаляет его с сессиями в `finally`. Значения последовательностей ID после тестов могут увеличиться.
